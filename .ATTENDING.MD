# “I’m Attending” flyer system

## Outcome

The repository now contains a production, versioned attending-flyer workflow:

- The supplied `public/images/WOW EXPERIENCE ATTENDING.png` artwork is the seeded 2000 × 2500 design.
- Super admins can upload the base design, position/resize normalized photo and name areas, test with a real photo/name, undo or redo 50 steps, discard, and save/publish.
- Public users can choose a photo, crop/reposition/zoom it with mouse, wheel, touch drag, or pinch, edit their name inline, and download/share a native-resolution PNG.
- Admin preview and public export call the same `renderFlyer` function. Export waits for `document.fonts.ready`.

## Upload error: root cause and fix

The old upload submitted the binary through a Next.js Server Action as `FormData`. Large artwork could therefore be rejected by the framework or deployment proxy body limit before Supabase Storage received it. It also coupled the binary upload to the signed-in session’s Storage RLS permissions.

The new flow is:

1. A super-admin-only Server Action validates the declared image type/size and creates a short-lived signed Storage upload URL.
2. The browser uploads the file directly to Supabase Storage.
3. A second super-admin-only Server Action verifies that the object exists and that its stored MIME type/size are valid, validates the complete geometry with Zod, and saves/publishes metadata.

This avoids the Server Action body-size path while preserving server-side authorization, validation, audit logging, and database-level super-admin policies.

## Data model and security

Migration: `supabase/migrations/20260928090000_attending_flyer_editor.sql`

It adds `base_width`, `base_height`, `config_version`, and a constrained JSONB `config`. Photo and text geometry use normalized coordinates and are validated by both Postgres checks and `flyerTemplateConfigSchema`. The migration replaces general flyer-management write policies with active `super_admin` checks for both the table and Storage objects. Public access remains read-only and limited to published templates.

## Seed

Apply migrations first, then seed the actual artwork into Storage:

```powershell
npx.cmd --yes supabase@latest db push --include-all
npm.cmd run seed:attending-flyer
```

The seed command reads `.env.local` and requires:

- `NEXT_PUBLIC_SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`

The SQL migration also inserts a same-origin `/images/...` published fallback row so the checked-in design is immediately represented in the schema. The seed script replaces that URL with the permanent public Storage URL.

## Main files

- `src/lib/flyer-template.ts` — versioned types, Zod schemas, defaults, sanitization, history helpers.
- `src/lib/canvas-utils.ts` — shared native-resolution renderer and text auto-fit.
- `src/lib/flyer-images.ts` — image validation, EXIF-aware decoding, HEIC capability handling, and large-image downscaling.
- `src/app/admin/(console)/flyer/page.tsx` — accessible template editor.
- `src/components/flyer/flyer-generator.tsx` — responsive public personalization/export studio.
- `src/actions/admin.ts`, `src/actions/public.ts`, and `src/lib/flyer-template-store.ts` — authorized persistence and published reads.
- `scripts/seed-attending-flyer.mjs` — idempotent Storage/database seed.
- `tests/flyer-template.test.ts` and `tests/flyer-pipeline.e2e.ts` — geometry, history, auto-fit, filename, and full render/export pipeline coverage.
